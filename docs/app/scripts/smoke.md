# `app/scripts/smoke.mjs`

Node (≥22 `fetch`) script that proves a deployed ResSpark URL serves the SPA and the API from one Worker (PLAT-01). Usage: `node app/scripts/smoke.mjs <baseUrl> [--auth] [--client-flow] [--connect-flow] [--esign-flow]`, or `pnpm -C app run smoke:auth <baseUrl> --auth` / `pnpm -C app run smoke:connect <baseUrl>` / `pnpm -C app run smoke:esign <baseUrl>`, which load the env files the `--auth` checks need without naming them in a shell command.

| Lines | What it does |
|-------|--------------|
| 3-4 | Imports `connectFlow` from `smoke-connect.mjs` (Plan 04-07; see `smoke-connect.md`) and `esignFlow` from `smoke-esign.mjs` (Plan 06-08; see `smoke-esign.md`). |
| 6-11 | Parses argv: the first non-flag argument is the base URL; missing → usage line on stderr and exit 1. |
| 12-16 | Strips a trailing slash; `--auth` enables checks marked `auth: true`; `--client-flow` also runs `clientFlow` at the end and implies `--auth`; `--connect-flow` and `--esign-flow` each imply `--client-flow`. |
| 18 | `isObject` guard, same shape as the SPA's. |
| 20-24 | `expectJson(res, status, test)`: asserts the status, parses JSON, and runs a predicate on the body; throws a one-line reason otherwise. |
| 26-27 | `isNotFoundEnvelope`: body is `{ error: { code: 'not_found', … } }`. |
| 29-49 | `staffToken()` (Plan 06): reads `SUPABASE_URL ?? VITE_SUPABASE_URL`, `SUPABASE_PUBLISHABLE_KEY ?? VITE_SUPABASE_PUBLISHABLE_KEY`, `DEMO_STAFF_EMAIL`, and `DEMO_STAFF_PASSWORD` from `process.env`; fails with a one-line reason naming the variables (never their values) when any is missing; signs in once with `POST {url}/auth/v1/token?grant_type=password` and the publishable key in the `apikey` header; caches the access token for the other checks. The token is never printed. |
| 50-52 | `session(init)`: a fetch to `<base>/api/admin/session`; the `signed_in` body. |
| 53-59 | `lookupFixture(headers)` (Plan 02-03): `POST <base>/api/admin/lookup` with `{ type: 'phone', value: '(555)010-0001' }`, the phone the fixture cases 900001 and 900002 share. |
| 61-68 | Plan 07 helpers: `expectPrivacyHeaders(res)` asserts `Cache-Control` contains `no-store`, `Referrer-Policy: no-referrer` and `X-Robots-Tag: noindex`; `invalidLink()` fetches `/c/not-a-valid-token` without following redirects. |
| 70-111 | `withProbeLink(body)` (`--auth`, Plans 07 and 02-07): needs `SUPABASE_URL`, `SUPABASE_SECRET_KEY` and `CLIENT_LINK_HMAC_KEY`. Dynamically imports `@supabase/supabase-js` (so the public checks stay dependency-free) and `node:crypto`. Re-finds the fixed probe case (Logics id `999999001`, the same fixture `requests-live.test.ts` uses, because events make cases undeletable) with `case_confirm_logics`, creates a one-item request with `request_create`, and sends it with `request_send` to get a real `client_links` row. Mints the token exactly like `worker/src/auth/client-link.ts` (HMAC-SHA256 over link id bytes plus big-endian `version`, base64url of id plus MAC) and passes `{ db, link, token }` to `body`. The `finally` block deletes the probe request, which cascades to its items, link, and `client_sessions` row. The token and RPC error details are never printed. |
| 113-126 | `linkExchange()` (Plan 07): requests `/c/<token>` on the deployed Worker and asserts 302 to `/c/`, a cookie with `rs_client=`, `HttpOnly`, `Secure`, `SameSite=Lax`, `Max-Age=86400` and without the token, the three privacy headers, and `opened_at` still `null`. |
| 128-160 | `clientPortal()` (Plan 02-07, PORT-01/02/05 deployed proof): exchanges the probe token for the `rs_client` cookie, then calls `/api/c/*` with the cookie and `X-Requested-With: ResSpark`. `GET /state` must be 200 with the privacy headers, `firm_name` `ValorTax`, `opened_at` `null`, one step, and no `request_id`, and must leave `opened_at` unset in the database. Two `POST /start` calls must return the same string `opened_at`, and the link row must then have it. `POST /heartbeat` with `{ last_step: 'smoke', user_agent_class: 'desktop' }` must return `{ ok: true }` and leave a `client_sessions` row with `last_step` `smoke`. `linkRow(db, id)` reads a link's `opened_at`. The cookie is never printed. The probe is deleted afterwards, so the count of opened links is unchanged across a run. |

It asserts the returned URL is `<base>/c/<64-char token>` at version 1, that opening it returns 302, that `POST .../copied` records the copy, and that `POST .../email` returns `ok: true` or `not_configured`. Plan 03-03 then reads `GET /api/admin/requests/:id/review` (the request id matches, there is at least one item, no item lists files before any upload, and `client_session` is `null` or has a `seen_at`: the row only appears after the portal's first heartbeat), expects `POST /api/admin/items/:itemId/approve` on the first item to answer 409 `item_not_submitted`, and expects `GET /api/admin/cases/:case_id/events?limit=5` to include this request's `request.sent` event. The `finally` block deletes the probe request with the service key, which cascades to its items and link, so the staff list stays clean. Failure messages name the method and path with the id masked as `:id`. The URL and token are never printed. |
| 210-265 | `checks` — the array later plans append to. `/admin` → 200, `text/html`, body contains `<div id="root"`; `/api/config` → 200 with string `app_env`, boolean `logics_write_enabled`, and `logics_mode` of `fake` or `live`, printed as `ok /api/config (logics_mode=fake)` (Plan 05-05; a check's `run` may return a detail string that the runner prints in parentheses); `/webhooks/smoke-probe` and `/api/nope` → 404 JSON `not_found` from the Worker (never `index.html`); `/c/ 404 html` → 404 `text/html` with the invalid-link heading; `/c/ headers` → the privacy headers on that 404; `/c/ spa` → `/c/` is 200 with `<div id="root"` and the privacy headers. |
| 266-282 | Plan 02-07 client-portal checks (PORT-06 deployed proof), no cookie and no `--auth`: `/api/c 401 no_session` expects `GET /api/c/state` to return 401 JSON with `error.code === 'no_session'` and the three privacy headers; `/api/c start 401` posts `/api/c/start` with `X-Requested-With: ResSpark` but no cookie and expects the same. Neither can open a link, so the count of opened `client_links` is unchanged across a run. |
| 283-308 | Plan 04-02 checks, no credentials: `webhooks truv 401` posts `{}` to `/api/webhooks/truv` with no signature and expects 401 JSON `error.code === 'invalid_signature'` (the route verifies before it reads anything else, and with no Truv secret on the Worker every Truv post is unverifiable); `webhooks unknown 404` posts to `/api/webhooks/nope` and expects the 404 `not_found` envelope; `webhooks docuseal 401` (Plan 06-08, D-18) posts `{}` to `/api/webhooks/docuseal` and expects the same 401 `invalid_signature` (the route checks the `X-Docuseal-Signature` HMAC before reading anything); `admin connections 401` reads `/api/admin/requests/<zero uuid>/connections` with no bearer and expects 401 `unauthorized`, proving the staff connection routes are mounted behind `staffAuth`. None writes anything. |
| 310-311 | `auth /c/ exchange` runs `linkExchange` (deployed proof of D-18); `auth /api/c portal` runs `clientPortal`. |
| 312-336 | `--auth` staff checks (PLAT-04/PLAT-07 on the deployed Worker): `auth signed_in` posts `{ event: 'signed_in' }` with the bearer and expects 200 `ok: true` with a numeric `event_id` (one real `staff.signed_in` row per run); `auth session` expects `GET` 200 with a string `firm_id`; `auth 401 without token` expects 401 `error.code === 'unauthorized'`. A failure message can include the response body, which never contains the token. |
| 337-369 | Plan 02-03 lookup checks (LOOK-01 deployed proof): `auth integrations status` expects `GET /api/admin/integrations/logics` 200 with `mode` `fake` or `live`; `auth lookup fixture` expects the fixture-phone lookup 200 with a `results` array, and exactly 2 results when `mode` is `fake` (in `live` the fixture phone is not a real case, so the count is not pinned); `lookup 401 without token` runs in every mode and expects 401 `unauthorized`. The lookup check never prints the response body. Between them, `auth request send` runs `requestSend` (REQ-01/02 deployed proof). |
| 371-381 | Runs each applicable check and prints `ok <name>` or `FAIL <name>: <reason>`. |
| 383-489 | `clientFlow()` (`--client-flow`, Plan 02-08, fake mode): the phase acceptance test on the deployed Worker, as staff and client would do it, on fixture case 900003 (the unique-phone fixture, so it never collides with the 900001 checks). Steps, each printed as `ok client-flow <step>`: `lookup` (`(555)010-0003` gives exactly one result, `logics_case_id` 900003), `confirm`, `templates` (finds `Standard resolution packet`), `create` (201 `request_id`), `send` (to `morgan.lee@example.com` / `(555) 010-0003`; the URL must match `https://<host>/c/<64-char token>`), `exchange 302` (`Location: /c/`, an `rs_client` cookie read with `getSetCookie()`, and no token in the body), `state unopened` (as many steps as the template has items; the Standard resolution packet has 6 since Phase 7's intake item, `opened_at` null, firm `ValorTax`, no contact details in the body), `start csrf 403` (a POST without `X-Requested-With` is refused), `start` (200 `opened_at`), `state opened` (`opened_at` set, status `opened`), `heartbeat` (200), `admin opened` (staff detail shows `opened` and `link.opened_at`), then with `--connect-flow` the `connectFlow` steps (Plan 04-07, on the same request and cookie, before revoke), then with `--esign-flow` the `esignFlow` steps (Plan 06-08, same request and cookie, also before revoke; it receives the link URL in memory for its `?step=` check), `revoke`, `revoke 401` (the same cookie now gets 401), `exchange 404` (the old URL serves the invalid-link page), then `ok client-flow complete request <id>` and, with `--connect-flow`, `ok connect-flow complete (keys: payroll yes|no, bank yes|no)`, and with `--esign-flow`, `ok esign-flow complete (keys: smarty yes|no, docuseal yes|no)`. The first failure prints `FAIL client-flow <step>: <reason>` and stops; a connect-flow or esign-flow failure is printed once by `connectFlow` / `esignFlow` as `FAIL connect-flow <step>: <reason>` (the error carries `reported`, so the catch here does not print it again). The `finally` block deletes the probe request with the service key (cascading items, link, and `client_sessions`); its audit events stay, because `events.request_id` has no foreign key. The URL, token, and cookie are never printed. |

## Notes

- Run from the repo root after `pnpm -C app run deploy`; the Plan 03 acceptance command is `node app/scripts/smoke.mjs "$(grep -oE 'https://[a-z0-9.-]+\.workers\.dev' docs/app/README.md | head -1)"`.
- Checks are independent; one failure does not stop the others, so the output lists every broken surface. `--client-flow` is the exception: its steps depend on each other, so it stops at the first failure.
- The Phase 2 acceptance command: `pnpm -C app run smoke:auth https://resspark.zh-a16.workers.dev --client-flow` (the script loads the env files, so no secret file is named in the shell).
- Phase 4 (Plan 04-02): the plain run must print `ok webhooks truv 401`, `ok webhooks unknown 404`, and `ok admin connections 401`.
- Phase 4 (Plan 04-07): `pnpm -C app run smoke:connect https://resspark.zh-a16.workers.dev` runs `--auth --connect-flow`. With no vendor keys it ends `ok connect-flow complete (keys: payroll no, bank no)`; with Sandbox keys both starts answer 200 and the admin list holds the two connections. See `smoke-connect.md` for each step.
- Phase 6 (Plan 06-08): the plain run must also print `ok webhooks docuseal 401`. `pnpm -C app run smoke:esign https://resspark.zh-a16.workers.dev` runs `--auth --esign-flow`; with no Smarty or DocuSeal keys it ends `ok esign-flow complete (keys: smarty no, docuseal no)`. See `smoke-esign.md` for each step.

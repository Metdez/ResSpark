## Phase Goal

**As a** tax-resolution client, **I want to** connect my payroll and my bank from the link on my phone, **so that** my pay stubs, W-2s, and 6 months of bank statements reach my case manager without me hunting for documents.

<objective>
Ship the connection framework as one proven slice: migration `0005_connections.sql` (the generalized `connections` representation plus secrets, bank rows, webhook ledger, consents, and the monotonic `connection_set_status` RPC), the generic signature-verified webhook route, the Truv HMAC and Plaid ES256 adapters, the queue consumer with retry/DLQ, and the `reconcileConnection` dispatcher whose payroll branch re-reads a Truv order and applies the result. Prove it live: a Truv `order-status-updated` fixture signed with the test secret → 200 → one `webhook_events` row → the consumer runs → the stubbed `GET /v1/orders/{id}/` returns two completed employers → `connection_set_status('done')` → `request_items.status = submitted` → `requests.status = waiting_on_staff` → event `connection.done`.

Purpose: every other Phase 4 plan (cron/Refresh, Truv documents, Plaid bank, both UIs) builds on this skeleton. The `connections` table and `BankProvider` interface are the primary representation (assumption-delta decision below); Plaid- and Truv-specific shapes live in `data jsonb` and the adapters.
Output: migration applied; `db/connections.ts`, `db/webhook-events.ts`, `webhooks/*`, `routes/webhooks.ts`, `jobs/{index,reconcile,payroll-reconcile}.ts`, `integrations/{provider-error,bank/provider,truv/client,truv/orders}.ts`; fixtures and signing helpers; live tests `connections-tracer.test.ts` and `connections-live.test.ts`; `rls.test.ts` covers the seven new relations; companion docs.
Scope note (plan-checker warning, accepted): the file count is high because every code file carries a companion doc under `docs/app/` (CLAUDE.md rule) and the slice needs its fixtures and live tests; the code itself is about 20 small modules on one data path (webhook → ledger → queue → reconcile → RPC). Splitting would leave a half-built path that no later plan can test, so the plan stays whole. If context runs short, the executor commits after each task and a continuation agent resumes from the last commit.
</objective>
